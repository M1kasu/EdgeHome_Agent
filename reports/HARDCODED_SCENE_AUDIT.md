# 固定场景与硬编码风险审计

审计日期：2026-07-15

范围：`custom_components/llama_conversation/edgehome`、`tests`、`README.md`、`reports`

结论：未发现“完整用户句子 -> 固定回复/固定结果”的核心主路径硬编码；但存在大量“场景关键词 -> 固定计划骨架/默认参数”的实现。它们适合早期演示和兜底，不适合作为参赛作品核心创新点。

## 1. 风险分级

| 风险 | 位置 | 类型 | 影响 | 处理建议 |
|---|---|---|---|---|
| 高 | `planner/demo_scenes.py:60-103` | 观影固定计划骨架 | “观影”容易表现为固定四设备动作 | 阶段 4 改为目标驱动规划，模板仅作测试基线 |
| 高 | `planner/demo_scenes.py:105-145` | 离家固定计划骨架 | 离家动作集合固定，约束表达不充分 | 阶段 4 由安全策略 + 状态快照动态生成 |
| 中 | `planner/templates.py:33-67` | 关键词场景识别 | “理解目标”仍依赖关键词入口 | 阶段 2/3 改为模型输出 `GoalSpec` |
| 中 | `planner/llm_planner.py:240-282` | 模板 fallback | 模型失败时仍可能进入固定演示计划 | 阶段 4 将 fallback 移出生产默认路径 |
| 中 | `coordinator.py:788-920` | 遗留直接场景函数 | 当前似乎未接主路径，但保留误用风险 | 阶段 4 删除或迁到测试辅助 |
| 中 | `planner/demo_scenes.py:254-277` | 正则默认参数 | 亮度默认 30%、温度默认 25.5 | 阶段 3 交给约束求解与策略计算 |

## 2. 未发现的问题

### 2.1 未发现完整句子到固定结果的生产主路径

审计没有发现类似下面这种主路径：

```python
if text == "帮我准备客厅观影场景":
    return fixed_plan
```

现有实现更多是：

- 先通过关键词识别 `SceneName`。
- 通过模型生成结构化计划。
- 模型失败时才允许受限 demo fallback。

这比完整句子匹配好，但仍不足以支撑“自主规划”叙述。

### 2.2 未发现模型直接调用 HA Service

`planner/llm_planner.py:93-126` 将模型限制为 JSON 计划输出；真实 HA service 调用在 `execution/executor.py` 中完成。

这是必须保留的安全设计。

## 3. 观影场景硬编码点

`planner/demo_scenes.py:70-78` 要求观影设备域固定为：

- `light`
- `cover`
- `switch`
- `climate`

`planner/demo_scenes.py:87-98` 观影计划的动作顺序为：

- 读取客厅状态。
- 窗帘不为 0 则关闭窗帘。
- 灯光未达到目标则调亮度。
- 电视未打开则打开电视。
- 未禁止空调时，设置空调制冷与温度。

`planner/demo_scenes.py:254-265` 存在默认参数：

- 亮度默认 `30`
- 温度默认 `25.5`

`planner/demo_scenes.py:275-277` 使用正则识别“不要开空调”。

评估：这是“状态感知的参数化模板”，不是完整固定句子，但也不是目标驱动规划。真正的目标驱动版本应根据光照、温度、用户约束、设备可用性、风险策略生成不同计划，并在缺信息时澄清。

## 4. 离家场景硬编码点

`planner/demo_scenes.py:107-121` 离家计划固定读取客厅、家庭与安全传感器。

`planner/demo_scenes.py:123-130` 默认关闭：

- 客厅主灯
- 客厅电视
- 客厅空调
- 客厅窗帘

`planner/demo_scenes.py:131-140` 默认启用安全模式。

评估：当前离家保护具备“受保护设备不纳入控制范围”的安全意识，但策略仍是固定动作集合。目标驱动版本应该先构建安全事实，如人在家、门窗开、设备离线、保护设备、能耗风险，再决定能执行、不能执行或需要确认的动作。

## 5. 场景关键词入口

`planner/templates.py:33-58` 固定关键词：

- 观影：`观影`、`看电影`、`电影模式`
- 离家：`离家`、`出门`、`我走了`
- 睡眠：`睡觉`、`晚安`、`睡眠模式`
- 回家：`回家`、`到家`
- 节能：`节能`、`省电`、`省电模式`

`planner/templates.py:61-67` 使用包含匹配。

风险：用户说“我要让客厅进入适合投屏的状态”时，未必能进入观影目标；用户说“人都走了但冰箱别动”时，也应通过语义理解成离家安全目标，而不是必须命中关键词。

## 6. 模板 fallback 风险

`planner/llm_planner.py:240-282` 的 `_scene_fallback()` 当前有两层保护：

- `scene is None` 时不 fallback。
- `_has_explicit_goal_constraints(goal)` 为真时不 fallback。

这能减少假动态风险。但参赛叙事中如果演示全靠 fallback，仍会被看出是模板系统。

阶段 4 处理建议：

- 默认关闭生产 fallback。
- 仅在测试或离线 demo 模式保留。
- UI 必须展示 `planning_source`。
- fallback 产生的计划不能被描述为“模型自主规划”。

## 7. 遗留直接场景函数

`coordinator.py:788-858` 的 `_async_handle_mqtt_movie_scene()` 会直接构建并执行 demo 观影计划。

`coordinator.py:860-920` 的 `_async_handle_deterministic_leaving_scene()` 会直接构建并执行 demo 离家计划。

审计观察：当前主路径在 `coordinator.py:303-313` 对命名场景返回 `handled=False`，让复杂规划入口处理；未在当前搜索中发现这两个遗留函数的调用点。

风险：它们仍在生产模块中，容易在后续改动中被误接回主路径。

处理建议：阶段 4 删除，或迁移到 `tests`/`scripts` 作为验收夹具。

## 8. 文档与验收报告风险

`README.md` 和既有 `reports/acceptance` 中已有多处 `READY_FOR_EXTERNAL_ACCEPTANCE` 与本地通过描述。这些可以保留为历史阶段证据，但后续参赛材料必须明确：

- 本地验收不等于外部验收。
- 模板 fallback 不等于模型自主规划。
- `31/31`、`20/20` 这类数字必须附原始证据链。

## 9. 阶段一结论

项目当前的创新底座是“本地 LLM 结构化计划 + HA 白名单执行 + MQTT 设备回读 + 安全守卫”，不是固定场景模板本身。

下一步必须把参赛展示重心从“我能执行观影/离家按钮式场景”转成：

- 用户提出目标。
- 系统感知环境。
- 系统抽取约束。
- 系统生成多个候选计划。
- 系统评估风险与收益。
- 系统执行可验证计划。
- 失败时诚实报告或重规划。

这样才能体现“智家端脑 EdgeHome”的自主规划价值。
