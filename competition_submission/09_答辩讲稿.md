# 答辩讲稿

## 5 分钟版本

各位评委好，我们的作品是“EdgeHome：面向端侧可信执行的智能家居大模型 Agent”。它解决的不是“让设备听懂一句命令”，而是让用户表达生活目标后，系统能够安全地把目标变成可执行、可验证的跨设备流程。

智能家居中，用户常要逐个操作灯、空调、窗帘；复杂场景需要事先配置规则。更关键的是，设备服务返回成功不一定代表状态真的改变。我们把这个问题拆成路由、规划、安全、执行和验证五个环节。

系统采用双路径。简单中文指令，例如“把客厅灯调到50%”，由轻量意图和槽位直接处理，再调用白名单工具并回读状态。复杂目标，例如观影、离家和睡眠，才交给本地模型生成结构化计划。模型计划仍要通过 Schema、参数限制、工具白名单、关键设备保护和冲突检查；执行后还必须回读状态。

这样设计既为了速度，也为了可靠。相同 Q4_K_M、ctx2048、CPU 环境的 50 条简单任务中，快速路径平均 12.652 毫秒，全部进入模型平均 643.195 毫秒。快速路径只接受 35 条确定性输入，剩余 15 条会保守降级，而不是勉强执行。

对于复杂场景，我们结合语言、温度、光照、人员和设备状态。例如用户要求观影且空调不能低于 25 度，计划会把温度下限当作约束，而不是只生成一段回答。原始 30 条复杂规划探针中，有 27 条通过 TaskPlan Schema。我们公开这不是 100%，三条失败没有进入设备层；其中一条确认在 256 token 上限处 JSON 截断，扩大预算的单条复测恢复为合法。其余两条原始文本未留存，因此我们不虚构错误内容。

安全方面，冰箱和路由器被列为受保护设备。20 条攻击性输入在隔离虚拟环境中均未调用受保护服务。可靠性方面，我们模拟服务返回成功但状态未改变：不做验证时最终完成率 90%、假成功率 10%；加入状态回读和一次受限恢复后，本次注入实验为 100% 和 0%。

系统还用本地 FTS5 检索设备资料，用确定性规则分析合成能耗数据。知识任务 19/20 返回本地证据，能耗分析 15/15 成功。一小时只读稳定性窗口记录 60 个样本，模型健康、检索和能耗失败均为零。

需要说明边界：当前只有 Q4 模型和 CPU 推理实测，没有宣称 GPU/NPU 加速，也没有完成完整八模块端到端消融。Home Assistant、Home LLM 和 llama.cpp 是开源基础；中文快速路径、场景安全闭环、检索、能耗和评测是本项目新增模块。我们的下一步是扩大真实设备和授权模型评测，同时坚持执行可验证、数据可追溯。谢谢各位。

## 8 分钟版本

使用 5 分钟版本作为主线，并增加以下三段，每段约 55–65 秒：

1. 在第 2 段后补充“为什么不用纯自动化”：自动化适合明确触发条件，但面对“把客厅弄舒服一点、空调别低于 25 度”仍需用户把生活语义手工拆成规则；EdgeHome 的作用是受限地完成这层转换，而不是取代已有自动化。
2. 在复杂场景段补充“为何结构化”：模型输出先被解析为 `goal` 和 `steps`，不合规 JSON 或未授权工具不能跨过执行边界；模型不可用时只有已注册虚拟场景允许模板降级。
3. 在实验段补充“指标如何读”：12.652 ms 是快速路由响应，27/30 是结构合法，100% 是隔离故障注入后的最终状态完成；三项不能互相替代。展示实验摘要和数据源索引。

## 12 分钟版本

在 8 分钟版本基础上，增加 4 分钟互动式展开：

1. 逐页讲解架构：状态快照、检索、能耗和资源调度如何只为受限计划提供证据，不扩大模型工具权限。
2. 播放 60–90 秒动态观影和离家演示，暂停展示保护规则和状态回读。
3. 展示 Schema 失败分析：原始 27/30、三条 ID、原文留存缺口、256 token 截断复测和 384 token 恢复；说明复测不是改写原始统计。
4. 展示开源边界、合成数据说明、离线网络条件和未来工作。保留至少 90 秒问答。

## 讲解提醒

- 把“模型输出”说成候选计划，不说成已经执行。
- 把“虚拟实体/隔离 HA”说清楚；不把它说成真实家庭的长期效果。
- 主动说出 CPU/Q4、单模型、非流式 TTFT 未测、消融未完成，能让证据链更可信。
