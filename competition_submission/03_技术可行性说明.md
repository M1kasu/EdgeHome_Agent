# 技术可行性说明

## 1. 运行可行性

系统已在 Windows Docker 环境完成 Home Assistant 与 llama.cpp 本地部署验证。第 13 阶段记录的 Home Assistant `check_config` 退出码为 0，重启后 Home Assistant 与 llama.cpp `/health` 均返回 HTTP 200。模型为本机实际存在的 `Home-Llama-3.2-3B.q4_k_m.gguf`，推理路径为 CPU。

## 2. 性能可行性

简单任务并不强制进入模型：50 条自然语言简单任务中，快速路径接受 35 条，平均 12.652 ms；相同任务全部进入模型平均 643.195 ms。复杂任务保留模型路径，以正确性和安全检查优先。结果来自真实本地端点，但不应外推为 GPU、NPU 或其他硬件性能。

## 3. 安全可行性

模型不能直接任意调用 Home Assistant。计划需要通过 Schema，后续执行还受工具白名单、参数检查、实体公开范围、受保护设备、冲突检测和状态验证限制。隔离攻击测试的 20 条输入没有调用冰箱或路由器，总服务调用为 0；该结论仅覆盖该测试集与虚拟实体。

## 4. 可靠性可行性

隔离 HA 故障注入模拟“服务返回但状态未更新”：无验证路径最终状态完成率 90%、假成功率 10%；加入状态回读和一次受限恢复后分别为 100% 与 0%。一小时只读稳定性窗口记录 60 次样本，模型健康、知识检索、能耗分析失败均为 0。

## 5. 离线与隐私可行性

内部 Docker 网络中，本地 `llama-server` 健康检查 HTTP 200、外部 DNS 请求失败，证明核心本地链路可在该受控断网条件下工作。资料检索使用本地 FTS5，能耗分析读取本地合成 CSV。该证明不覆盖在线天气、翻译等外部 Home Assistant 集成。

## 6. 可复现性

工作负载、CSV/JSONL、图表生成脚本、容器编排和测试均纳入仓库。提交包 `assets/data/` 保存制作图表的最小数据副本，`scripts/` 提供启动、健康检查、重置和图表生成入口。

## 7. 风险控制

复杂 Schema 原始测试为 27/30 合法，不将其夸大为 100%。其中一条在 256 token 上限处确认截断，并在 384 token 单条复测恢复；另两条因原始文本未留存不能确定具体错误。正式展示准备模板降级、预录镜头和命令行验证，详见 `12_故障应急预案.md`。
