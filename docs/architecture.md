# EdgeHome 架构

用户输入先经过确定性的中文快速路径；不能安全处理的复杂请求才进入本地模型规划。复杂目标会先被抽取为 `GoalSpec`：目标类型、房间、用户偏好、禁止项、参数下限和澄清需求都以结构化字段保存。规划器再读取统一 `HomeStateSnapshot`，把环境、设备能力、当前状态和安全边界合并为可裁剪上下文。模型或目标策略只允许返回 `TaskPlan` JSON，随后依次经过 Pydantic、工具白名单、实体暴露、参数、冲突、受保护设备和环境状态校验。FixedPlanExecutor 调用 Home Assistant 服务后重新读取状态验证结果。

每个候选计划都会附带 `RiskAssessment` 与 `PlanScore`。风险评估用于解释受保护设备、危险工具、缺失前置条件和需要回读的证据；计划评分用于标记约束覆盖、设备匹配、状态利用和安全余量。工作台读取 `sensor.edgehome_last_execution`，把目标画像、计划步骤原因、预期结果、风险、评分和 MQTT/HA 回读证据放在同一页，避免只展示“模型说成功”。

本地知识和能耗入口为只读路径。模型提示只包含任务相关且预算裁剪后的环境快照；执行重校验仍使用完整的受限快照。

第 12 阶段把知识资料以 Markdown + SQLite FTS5 部署到本机，检索结果包含来源与段落，缺少证据即拒绝回答。能耗 CSV 经严格装载和确定性分析后才生成结构化 JSON；模型不读取原始记录。只有用户确认的白名单建议会转换为可撤销的 EdgeHome Demo 运行时自动化，冰箱和路由器永远不在节能目标集合中。

第 13 阶段在路由前加入输入长度边界；复杂规划通过资源感知调度器排队。资源警戒或模型不可用时仅允许受限目标策略处理已注册场景，安全事件保持确定性路径。`benchmark` 包将单调计时、系统资源快照和 JSONL/CSV 结果从业务代码中隔离出来。

目标驱动改造阶段把观影和离家从固定动作模板迁移为受约束策略：同一“观影”目标会因亮度下限、空调禁止、当前光照/温度和房间不同而产生不同计划；离家目标会先检查人在、门窗和受保护设备，无法安全满足时阻断而非继续执行。`scripts/accept_goal_agent.py` 提供离线验收框架，输出 `reports/goal_agent_acceptance/` 中的 GoalSpec、计划、风险评分和结果摘要；它证明本地策略证据链可生成，但不替代独立外部黑盒验收。
